## 決裁事項の例

### DEC-001: 認証方式の選定

**提案者:** PM
**優先度:** 高
**期限:** 2024-02-10

#### 背景

ログイン機能の実装にあたり、認証方式を決定する必要があります。
将来的なマイクロサービス化も視野に入れた選定が求められます。

#### 選択肢

1. **JWT (JSON Web Token)**
   - メリット:
     - ステートレスで水平スケールしやすい
     - マイクロサービスアーキテクチャに適している
     - モバイルアプリとの統合が容易
   - デメリット:
     - トークンの無効化が難しい
     - トークンサイズが大きい
   - 工数: 3日

2. **Session-based 認証**
   - メリット:
     - サーバー側で簡単に無効化できる
     - セキュアでシンプル
     - 実装が容易
   - デメリット:
     - セッションストアが必要（Redis等）
     - 水平スケールに制約
   - 工数: 2日

#### 推奨案

**JWT** を推奨します。

理由:
- 将来的なマイクロサービス化を見据えて
- フロントエンドとAPIの分離が明確
- モバイルアプリ対応の可能性

#### 影響範囲

- ファイル:
  - `apps/api/src/auth/`
  - `apps/web/src/hooks/useAuth.ts`
  - `packages/shared/src/types.ts`
- 機能:
  - ログイン
  - ログアウト
  - トークンリフレッシュ
- スケジュール:
  - 実装: 3日
  - テスト: 1日

#### 決裁待ち中に実装可能な部分

この決裁と無関係に進められるタスク：
- [x] ユーザー登録画面（認証方式に依存しない）
- [x] プロフィール画面
- [ ] パスワードリセット画面（UIのみ）

#### 部長の判断

**決定内容:**
JWT を採用します。

**決定日:** 2024-02-08

**理由・補足:**
将来的なマイクロサービス化を考慮して JWT を選択。
ただし、トークンの有効期限を短く設定し、リフレッシュトークンを導入すること。

## 決裁フロー

```
1. PMが決裁事項を特定
   ↓
2. state/decisions.md に記録（DEC-XXX）
   ↓
3. 部長に通知（日次スタンドアップまたは即時）
   ↓
4. 決裁待ち中に実装可能な部分を先に実装
   ↓
5. 部長が判断を記入
   ↓
6. PMが決定内容を反映して実装指示
   ↓
7. 決裁済みに移動
```

## エスカレーション基準（再掲）

### PMが部長に確認すべきこと

- 要件の解釈に迷うとき
- 工数が当初想定の1.5倍を超えそうなとき
- 技術選定で大きな選択肢があるとき
- 機能の追加・削除
- 外部サービス・ライブラリの新規導入
- セキュリティに関わる重要な判断
- パフォーマンスとセキュリティのトレードオフ
